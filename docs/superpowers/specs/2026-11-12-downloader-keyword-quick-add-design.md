# 下载器收件箱：搜索词一键加入白名单 / 黑名单（简短设计）

> 2026-11-12 用户确认方案。属于小改动，只写简短设计。

## 意图

用户在下载器收件箱里搜一个词、看到命中的资源包后，希望不离开页面就把这个词加进关键词库：
- 加黑名单：标题含这个词的资源包立刻从「待确认」里移走；
- 加白名单：标题含这个词、原本在「未命中」的资源包立刻变成候选。

现状：匹配规则已经支持白名单出候选、黑名单排除（`app/services/downloader/sync_service.py::_match_package`），但只在资源包同步时执行（现在 6 小时一轮），而且加词要去关键词页。

## 目标 / 非目标

- 目标：搜索框旁两个按钮；确认前预览影响数量；确认后立即生效。
- 非目标：不改匹配规则本身（仍是「归一化后标题包含该词」）；不联动 Jellyfin / 115 删除（那是第 2 点的事）；不新建数据表。
- 反目标：一个短词误伤大量候选而用户事先不知道。

## 方案

考虑过的做法：
1. **加词后只重算受影响的资源包，预览走同一套代码再回滚（选用）**：预览和实际结果必然一致；只处理标题含该词的包，几百毫秒级。
2. 加词后全量重算 2.5 万个资源包：最简单，但一次要几十秒，且预览需另写一套计数逻辑，可能与实际不一致。
3. 只加词、等下一轮同步：零开发，但最多要等 6 小时，不满足「立即」。

## 设计

后端（`app/api/routes/downloader.py` + 下载器服务）：
- `POST /downloader/keyword-quick-add`，参数 `keyword`、`list_type`（whitelist / blacklist）、`dry_run`。
- 流程：校验 → 写入关键词（`create_entry_no_commit`，普通优先级）→ 用最新规则重算「归一化标题包含该词」的资源包（复用 `_load_terms` + `_match_package`）→ 统计结果。
  - `dry_run=true`：统计后回滚，什么都不写。
  - `dry_run=false`：提交。
- 返回：受影响资源包数、移走的候选数、新增的候选数、最多 5 个示例标题、关键词是新建还是已存在。
- 校验：
  - 归一化后少于 2 个字符 → 拒绝（与别名规则一致）；
  - 该词（或其别名）已在关键词库且类型不同 → 拒绝，提示去关键词页修改，不在这里悄悄改类型；
  - 已存在且类型相同 → 不重复建，只重算一遍（可用于补救）。

前端（`frontend/src/pages/downloader/CandidatesInbox.tsx`）：
- 搜索框有内容时，旁边显示「加入白名单」「加入黑名单」两个按钮。
- 点击后先调用预览，弹窗显示：将新增多少候选 / 移走多少候选 / 涉及多少资源包 + 示例标题；黑名单用红色确认按钮。
- 确认后执行，提示结果，刷新列表和各视图计数。

## 已知限制（我的判断，用户可推翻）

- 撤销：在关键词页删除或停用该词即可；被黑名单移走的候选要等下一轮同步（或手动点「同步资源包」）才会回来。
- 词库变更会记入关键词操作日志（复用现有 `create_entry` 日志）。
