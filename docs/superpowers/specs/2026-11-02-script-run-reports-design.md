# 阶段 6：Unraid 脚本日报 设计

> 日期：2026-11-02
> 状态：待用户确认
> 范围：`DEL_SOMETHING` 和 `MOVE_SSD_CACHE_TO_DISK2` 两个脚本的运行结果回报与页面展示。不做系统接管。

## 一、背景与目的

两个脚本每天在 Unraid 上自动运行，用户很少看日志，因为 `log.txt` 内容太多。用户想知道的是：`DEL_SOMETHING` 清理了多少、新命中了多少。`MOVE_SSD_CACHE_TO_DISK2` 基本是纯搬运，没有太多实质信息。

现状：

| 脚本 | 运行时间（服务器时间） | 输出 | 问题 |
|---|---|---|---|
| `DEL_SOMETHING` | 每天 12:09 | 约每次 1000 多行，大部分是 `[ALREADY-PLACED]` | 关键数字要自己数 |
| `MOVE_SSD_CACHE_TO_DISK2` | 每天 01:01 | 结尾有一行总结 | 要专门打开日志才看得到 |

两份运行日志都在 `/tmp/user.scripts/tmpScripts/` 下，服务器重启后应该会丢失，不能当历史记录用。

## 二、目标 / 非目标 / 反目标

**目标**

1. 脚本每次运行结束（包括中途出错）后，把统计和名单回报给 18x。
2. 18x 新增「脚本日报」页面，用趋势图和运行记录展示，点开一次运行能看到具体名单。
3. 到点没有收到回报时，页面明确显示“没有运行记录”。

**非目标**

- 由 18x 接管或触发脚本执行。
- 改变脚本的清理、移动规则，以及两个 Python 整理脚本的内容。
- 导入历史日志（趋势图从上线当天开始累积）。
- 显示某个文件是被哪个黑名单词删除的（现有输出没有这个信息，要改 Python 脚本）。
- 主动推送提醒（用户选择在页面里看）。

**反目标（即使能跑也算失败）**

- 回报失败、18x 宕机或回报超时，影响清理和搬运，或改变脚本退出码。
- 页面提供删除、移动等任何会改动媒体文件的操作。
- 把真实文件名、账号密码写进代码、测试夹具、文档或 18x 应用日志。
- 重复回报同一次运行产生重复记录。

## 三、用户已确定的内容

- 在 18x 页面里看，不做推送。
- 布局选 B：上方是最近 7 天的趋势图，下方是运行记录。
- 点开一次运行能看到**具体名单**，因此 18x 数据库会保存真实文件路径。

## 四、整体结构

```
Unraid 脚本（bash）
  ├─ 原有逻辑不变，输出同时写入本次运行的临时文件
  └─ 结束时（trap EXIT）调用 report_script_run.py
        ├─ 解析临时文件 → 统计 + 名单
        └─ 登录 18x → POST /script-runs
18x
  ├─ script_runs / script_run_items 两张表
  ├─ 查询接口（趋势、运行记录、名单）
  └─ 「脚本日报」页面
```

## 五、各部分设计

### 1. 回报脚本 `scripts/unraid/report_script_run.py`（新增）

- 只用 Python 标准库，放进仓库；部署时复制到 `/mnt/cache/docker1/python/scripts/delsomethin/`。
- 参数：脚本名、运行开始时间、退出码、本次输出文件路径、凭证文件路径。
- 登录复用 `DEL_SOMETHING/.env` 里的 `KEYWORDS_API_USERNAME` / `KEYWORDS_API_PASSWORD`，不新增账号，也不打印凭证。两个脚本都读这一份。
- 回报 ID 由脚本名和开始时间组成，保证重复回报不会产生重复记录。
- 网络失败最多重试 3 次，每次超时 30 秒；仍失败就打印一行提示并以 0 退出。
- 失败时不落地缓存。这次运行的结果会缺失，页面显示为“没有运行记录”。

### 2. `DEL_SOMETHING` 输出解析

| 输出 | 归类 | 进名单 |
|---|---|---|
| `[DELETED] 已删除目录：` | 清理-目录 | 是 |
| `[DELETED] 已删除文件：` | 清理-文件 | 是 |
| `[EMPTY]` | 清理空文件夹 | 是 |
| `[MOVED] 源 -> 目标` + 下一行 `命中标准词:` | 见下 | 是，含来源、目标、关键词 |
| `[AMBIGUOUS-LOW]` | 词条有歧义 | 是 |
| `[SKIPPED]` | 跳过（文件过大） | 是 |
| `[ERROR]`、`[错误]` | 报错 | 是 |
| `[WARN]` | 警告 | 是 |
| `[ALREADY-PLACED]` 及其命中行 | 不统计 | 否 |
| `[SUMMARY]` 段、`[INFO]`、`[SKIP]` 等 | 忽略 | 否 |

- `[MOVED]` 的来源在 `已整理/抖音` 或 `已整理/抖音风` 下时归为“重新归位”，其余归为“新命中”。趋势图的“新命中”只算后者。
- 一行解析不了时不让回报失败，计入“未识别行数”，方便发现脚本输出格式变化。

### 3. `MOVE_SSD_CACHE_TO_DISK2` 输出解析

- 以结尾的 `完成: 移动 X 个, 删除重复 Y 个, 跳过 Z 个, 失败 N 个` 为准。
- 名单只保留失败和跳过，不保留每个移动项。
- 没有“完成”这一行（中途退出）时，状态记为失败。

### 4. 生产脚本改动（两个脚本相同的思路）

- 在 `flock` 判断之后加入：把标准输出和错误同时写到本次运行的临时文件，并设置 `trap` 在退出时调用回报脚本。
- 被 `flock` 拦下的重复运行不回报。
- 演练模式（`DRY_RUN=true`、`--dry-run`）不回报。
- 原有 `log.txt` 内容不变，只多一行回报结果。
- 临时文件回报后删除。

### 5. 数据模型（迁移 `0017`）

**`script_runs`**：`id`、`run_key`（唯一）、`script_name`、`started_at`、`finished_at`、`exit_code`、`status`（success / warning / failed）、`counts`（JSON）、`items_truncated`、`received_at`。

**`script_run_items`**：`id`、`run_id`（外键，级联删除）、`kind`、`path`、`target_path`、`keyword`、`message`。按 `run_id + kind` 建索引。

- `status`：退出码非 0 或有报错为 failed；只有警告或歧义为 warning；其余为 success。
- 每次运行名单上限 5000 条，超出时 `counts` 仍是准确总数，`items_truncated=true`，页面提示名单不完整。目前观察到的单次最大值约 300 多条。
- 名单保留 90 天，统计长期保留。每次收到回报时清理一次过期名单。
- 时间存 UTC，页面按用户本地时间显示。

### 6. 接口

沿用现有路由风格；登录由全局认证中间件校验，这些接口不加入公开路径。回报脚本经 nginx 访问 `http://192.168.70.138:8010/api/script-runs`（与现有脚本读取关键词同一入口，nginx 请求体上限 100 MB，够用）。

| 接口 | 作用 |
|---|---|
| `POST /script-runs` | 接收回报；相同 `run_key` 不重复写入，返回已有记录 |
| `GET /script-runs/summary?days=7` | 每天清理数、新命中数（趋势图）和两个脚本的今日运行状态 |
| `GET /script-runs?limit=&offset=` | 运行记录 |
| `GET /script-runs/{id}/items?kind=&limit=&offset=` | 名单，分页 |

**没有运行记录的判断**在查询时计算，不依赖定时任务：按固定运行时间（`DEL_SOMETHING` 12:09、`MOVE` 01:01，Asia/Shanghai），超过 2 小时仍没有当天记录，就显示“今天没有运行记录”。

> 运行时间写成 18x 配置项。Unraid 上改了定时，要同步改这里，否则会误报。

### 7. 页面

- 路由 `/script-runs`，导航放在「流程」组，名称「脚本日报」。
- 上方两张柱状图：最近 7 天 `DEL_SOMETHING` 的清理数和新命中数，每根柱子标数字。没有运行的那天显示为“无记录”，不显示成 0。项目没有图表库，用普通样式实现，不新增依赖。
- 下方运行记录，时间倒序，两个脚本混排，每行一句话加状态标记，参考草图 `.superpowers/brainstorm/32440-1793586085/content/script-report-layout-v2.html`（不提交）。
- 点一行展开名单，按类别分页签（清理、新命中、重新归位、空文件夹、问题），每页 50 条，支持在当前类别内搜索路径。
- 只有查看功能。

## 六、配置

- `SCRIPT_REPORT_SCHEDULES`：两个脚本的预期运行时间，有默认值。
- 回报脚本读取 `DEL_SOMETHING/.env`，不新增凭证。

## 七、验收标准

1. 解析测试：用虚构文件名的夹具，覆盖上面表格的每一类，包括 `[错误]`、多行 `[MOVED]`、未识别行、缺“完成”行。
2. 接口测试：重复回报不产生重复记录；未登录被拒绝；过期名单被清理；超过 5000 条时计数仍准确。
3. 停掉 18x 后运行回报脚本：约定时间内结束，退出码为 0。
4. 脚本模拟失败（退出码非 0）：原退出码不变，页面显示失败。
5. 生产运行一次 `MOVE` 和一次 `DEL_SOMETHING` 后：页面数字和当次 `log.txt` 手工统计一致，名单能点开。
6. 演练模式不产生记录。
7. 用户在页面确认。

## 八、留给实施者的决定

- 输出同时写入临时文件的具体 bash 写法，要保证 `trap` 运行时内容已写完。
- 接口请求体的具体结构、前端组件拆分。
- `counts` 的键名。

## 九、主要风险

| 风险 | 处理 |
|---|---|
| 脚本输出格式以后变化，统计失真 | 记录未识别行数；页面在该数大于 0 时提示 |
| 改生产脚本出错，影响每日清理 | 改前备份；先单独运行 `MOVE`，再运行 `DEL_SOMETHING`；回滚即恢复备份 |
| `/boot` 上的脚本不随代码部署更新 | 部署说明写明位置；回报脚本版本不匹配时只影响统计 |
| 数据库保存真实路径 | 只在登录后可见；不写应用日志；保留 90 天 |

## 十、需要用户单独批准的操作

1. 生产数据库迁移（新增两张表）。
2. 修改 Unraid 上两个脚本，并放置回报脚本。
3. 部署 18x，以及上线时手动触发两个脚本各运行一次。其中 `DEL_SOMETHING` 会真实执行清理，也可以等它 12:09 自然运行。

## 十一、回滚

- 恢复两个脚本的备份，脚本立即回到原样。
- `.env` 不变，回报脚本可保留或删除。
- 18x 回退版本后，两张新表不影响其他功能；需要时用迁移回退删除。
