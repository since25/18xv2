# Jellyfin 第一版：按关键词合集浏览与播放 设计

> 日期：2026-11-01
> 状态：待用户确认
> 范围：只覆盖第一版（本地「已整理」+ 带 NFO 的 115 STRM 进入独立 Jellyfin，按关键词分合集，能播放，115 走 302）。

## 一、背景与目的

18x_v2 已是关键词体系的唯一来源：Unraid 上的 `DEL_SOMETHING` 和 `MOVE_SSD_CACHE_TO_DISK2` 两批脚本通过 `/api/keywords` 读取白名单，把本地资源按关键词归到 `/mnt/disk2/qbbtdn/已整理/<关键词>/`。115 一侧也已有大量 STRM（带番号和 NFO），目前挂在 Emby 里。

用户希望以 18x_v2 为中心，再串联一个开源 Jellyfin：

- 两类资源（本地、115 STRM）都进 Jellyfin；
- 打开 Jellyfin 能**按关键词（合集）浏览**，点开就能**播放**；
- 115 内容外网播放走 **302**，流量不经过家里上行；
- Jellyfin 与现有 Emby **各自独立运行，互不影响**。

## 二、目标 / 非目标 / 反目标

**目标**

1. 部署独立的 Jellyfin 容器，只读挂载本地「已整理」与指定 STRM 目录。
2. 18x_v2 扫描这两类资源，建立「关键词 → 媒体位置」对应。
3. 18x_v2 通过 Jellyfin API 按关键词维护合集；一个视频命中多个关键词时进入多个合集。
4. 在 Jellyfin 前放现成的 302 反向代理：新起一个 MediaWarp 实例，配置照抄现有 Emby 那个实例。外网播放 115 内容时，客户端跳转到 115 直链。
5. 家里和外网各实测一次播放通过。

**非目标（第一版不做）**

- 无 NFO 资源的封面、人物头像、社交链接抓取（后续阶段 3）。
- 关键词「主体类型」（人 / 系列 / 频道）字段（后续阶段 3）。
- 115 目录树定期快照映射（后续阶段 4）。
- 115 视频下载截帧（后续阶段 5）。
- 两批 Unraid 脚本的运行结果回报与执行接管（后续阶段 6）。
- SSD_cache 上的「已整理」中转目录（内容最多停留一天，次日 01:01 移到 disk2）。
- 普通影视 STRM（`mp302_*`、`alist_*` 等）。
- `porn_tv1`（115 直接映射的源 STRM）。其中被 MDC 刮削过的部分已经以硬链接形式出现在 `302porn_tv1`，再纳入会重复；没刮削过的约 1000 个归入后续"115 无 NFO 资源"阶段。
- 自研 302 网关；改动现有 Emby 前面的 MediaWarp 实例。

**反目标（即使能跑也算失败）**

- Jellyfin 或 18x 往媒体目录写入任何文件（图片、NFO、改名），或改动 Emby 的目录与配置。
- 合集同步删除或改动用户在 Jellyfin 里手工建的合集。
- 关键词匹配不上时"猜"一个关键词塞进合集。
- 本项目为第一版对 115 发起任何新的接口调用（302 解析由代理经 OpenList 完成，属于正常播放行为）。

## 三、现状数据（2026-11-01 只读抽查）

| 来源 | 路径 | 规模 | 结构 |
|---|---|---|---|
| 本地已整理 | `/mnt/disk2/qbbtdn/已整理` | 约 758 个顶层目录、约 3.2 万个视频、3.1T | `<关键词>/<资源包>/<视频>`；组合关键词目录以 `__` 连接，如 `甲__乙` |
| 115 番号 STRM（MDC 刮削产物，**纳入**） | `alist-strm/video/302porn_tv1` | 约 6900 个 strm，NFO 基本齐全 | MDC 按 `{actor}/{number}` 生成：`<演员>/<番号>/<番号>.strm + .nfo + 图片` |
| 115 直接映射 STRM（MDC 的源，**不纳入**） | `alist-strm/video/porn_tv1` | 约 7300 个 strm，其中约 6300 个与上一行是硬链接 | 115 目录原样映射 |

- 两层来源关系：`porn_tv1` 是 alist-strm 按 115 目录直接生成的 STRM；MDC 容器以它为源，刮削后用硬链接输出到 `302porn_tv1`。同一个视频在两边各有一个 .strm，所以只纳入 `302porn_tv1`。
- STRM 内容是 OpenList 的局域网 HTTP 地址（`http://<内网>:5244/d/115_OPEN/...`）。外网客户端直接访问不到，所以必须靠代理做 302。
- **现有 302 链路已在生产可用**：Unraid 上已有一个 MediaWarp 容器（宿主机 9001 端口）挂在 Emby 前面，配置是 `http_strm` 开启、`final_url: true`（服务器侧跟随 OpenList 跳转，再把最终直链 302 给客户端）、`proxy: false`（只直接播放），前缀为 `/mnt/user/docker1/alist-strm/video/`。
- NFO 里有 `<actor><name>`、`<tag>`、`<studio>`，海报和背景图已在目录里。
- Emby 以可写方式挂载 `/mnt/user/docker1/alist-strm`；Jellyfin 必须只读挂载，避免互相覆盖。
- 18x 容器目前以 `/mnt/cache/docker1/alist-strm/video` 路径挂载 STRM 目录（Emby 媒体动作模块在用），没有挂载 disk2。

## 四、整体结构

```text
外网/家里客户端
      │
      ▼
 Lucky 反代（已有）──► MediaWarp-Jellyfin（新实例）──► Jellyfin（新容器）
                         │  播放 115 STRM 时：                │ 只读挂载
                         │  解析 OpenList /d/ 地址 → 302 到 115 直链
                         ▼                                      ▼
                      OpenList（已有）              disk2/已整理、302porn_tv1

 （现有链路不动：Lucky ──► MediaWarp（9001）──► Emby）

 18x_v2（已有）
   ├─ 扫描两类媒体（只读）→ 关键词映射
   └─ 调 Jellyfin API → 按关键词建 / 更新合集
```

职责划分：

- **Jellyfin**：媒体库与播放。不联网刮削，不写入媒体目录。
- **MediaWarp**：只做播放请求改写与 302。本地文件和非 STRM 请求原样转给 Jellyfin。
- **18x_v2**：关键词映射与合集同步。不参与播放链路。

## 五、各部分设计

### 5.1 Jellyfin 部署

- 编排文件放在 `docker/jellyfin/`（按 AGENTS.md 约定 Docker 配置放 `docker/`），与 18x 主 compose 分开，可独立启停。
- 配置目录放在 `/mnt/cache/docker1/jellyfin/`，与 Emby 的配置目录分开。
- 媒体目录一律 `:ro` 挂载，容器内路径与宿主机路径保持一致：STRM 用 `/mnt/user/docker1/alist-strm/video/302porn_tv1`（与 Emby、MediaWarp 前缀一致），本地用 `/mnt/disk2/qbbtdn/已整理`（与整理脚本一致）。
- 媒体库：
  - 「115 番号」：只包含 `302porn_tv1`。读取本地 NFO 和图片；关闭所有在线元数据下载器；关闭"保存图片 / NFO 到媒体文件夹"。
  - 「本地已整理」：包含 `/mnt/disk2/qbbtdn/已整理`。不联网刮削，标题用文件名；同样关闭写入媒体文件夹。库类型由实施者实测后选定（见第八节）。
- 两个库都开启定时扫描（每天一次，放在 01:01 移盘脚本之后，例如 02:30），可选开启实时监控。

### 5.2 302 代理（第二个 MediaWarp 实例）

- MediaWarp 一个实例只能接一个媒体服务器，所以**新起一个实例**专门接 Jellyfin。现有 Emby 前的实例（9001）和它的配置目录完全不动。
- 新实例使用独立的配置目录（如 `/mnt/cache/docker1/mediawarp-jellyfin/`）和不冲突的宿主机端口；编排放在 `docker/jellyfin/`。
- 配置以现有实例为模板：
  - `server.type: Jellyfin`，地址指向新 Jellyfin，认证填 Jellyfin 的 API Key；
  - `http_strm` 照抄：开启、`final_url: true`、`proxy: false`，前缀为 `/mnt/user/docker1/alist-strm/video/`；
  - 只对 Emby 生效的功能（字幕转换、外置播放器、Emby 前端脚本）不开；`alist_strm` 是否保留由实施者对照现有实例的实际命中情况决定。
- Lucky 外网入口指向新实例端口，**不直接暴露 Jellyfin 端口**。
- 本地「已整理」视频不走 302，由 Jellyfin 直接串流（外网播放会占家里上行，这是已接受的取舍）。

### 5.3 18x_v2：媒体扫描与关键词映射

- 18x 容器新增两条只读挂载，路径与 Jellyfin 内一致：`/mnt/disk2/qbbtdn/已整理`、`/mnt/user/docker1/alist-strm/video/302porn_tv1`。现有 `/mnt/cache/...` 挂载保持不动（Emby 媒体动作模块在用）。
- 扫描只读目录元信息，不读视频内容、不计算哈希。
- 关键词匹配复用现有关键词库（规范名 + 别名，按现有归一化规则），**只匹配白名单关键词**：
  - **本地**：取顶层目录名，按 `__` 拆成若干段，每段匹配一个关键词。顶层目录下的所有视频归属这些关键词。
  - **115 STRM**：先用 NFO 的 `<actor><name>` 逐个匹配；没有 NFO 或演员匹配不上时，再用顶层目录名（MDC 生成的演员目录）匹配。
  - 匹配不上的条目记为「未匹配」，在页面列出，不猜测。
- 扫描结果落库，至少记录：来源（本地 / 115_strm）、路径、命中的关键词（多对多）、最近一次扫描时间。路径消失的条目在下次扫描时标记失效，不物理删除历史记录。
- 触发方式：页面手动触发；另有每天一次的低频后台任务（Jellyfin 定时扫描之后，例如 03:00）。复用现有后台任务机制，同一时间只跑一个。

### 5.4 18x_v2：合集同步

- 通过 Jellyfin API（API Key 放 `.env`，只引用变量名，不写进代码和文档）：
  1. 按路径查出 Jellyfin 条目 ID。Jellyfin 尚未扫描到的条目，等下次同步再处理。
  2. 每个"有命中的关键词"对应一个合集，合集名用关键词规范名。
  3. 增量同步：只增删差异部分。
- 18x 只管理自己创建的合集：本地记录「关键词 ↔ 合集 ID」，并给合集打统一标记（如标签 `18x-managed`）。没有标记的合集一律不碰。
- 关键词改名时同步改合集名；关键词停用或合并后，对应合集清空并删除（只限带标记的）。
- 同步结果在页面显示：合集数、新增和移除的条目数、找不到 Jellyfin 条目的路径数、未匹配数。

### 5.5 页面

在现有前端加一个「Jellyfin」页面（具体位置由实施者按现有导航分组决定）：

- 显示扫描和同步状态，以及最近一次的结果摘要；
- 「立即扫描」「立即同步合集」按钮；
- 未匹配列表（路径 + 来源），便于用户回关键词页补别名。

### 5.6 后端细化（2026-11-01 后端审查后补充，以本节为准）

**数据表（新建，不复用 tree_nodes / node_files / keyword_hits / emby_media_mappings，它们分别属于导入快照或 Emby 映射）：**

- `jellyfin_media_items`：id、source（local / strm_115）、path（与 source 联合唯一）、file_ext、size、mtime、active、first_seen_at、last_seen_at、last_seen_job_id、jellyfin_item_id、resolve_state（pending / resolved）、match_state（matched / unmatched / nfo_error）、match_note。
- `jellyfin_media_keywords`：media_item_id、keyword_entry_id（ON DELETE CASCADE）、match_source（folder_segment / nfo_actor / folder_fallback）、raw_term；(media_item_id, keyword_entry_id) 唯一。
- `jellyfin_keyword_collections`：keyword_entry_id（可空，ON DELETE SET NULL，关键词被合并删除后留下"退休"记录供清理）、jellyfin_collection_id、canonical_name_snapshot、status（active / retired / conflict）、last_sync_at、last_error。
- 不在本地保存合集成员表：同步时读 Jellyfin 合集现有成员，与应有成员做差集。
- 运行状态复用现有 `background_jobs`（任务类型 `jellyfin:scan`、`jellyfin:sync`）。新表要有 Alembic 迁移，并在 `alembic/env.py` 中导入。

**扫描：**

- 只收媒体文件：本地按视频扩展名白名单；115 侧只收 `.strm`。`.nfo` 和图片只作为元数据。
- 每次扫描都按**当前关键词库**全量重算匹配（约 3.9 万条，内存字典匹配，成本低）。这样关键词停用、改名、改别名、合并后，下一次扫描自然生效，**不往关键词模块里加钩子**。
- 按 500～1000 条分批提交。只有完整扫描成功后，才把本次未见到的条目标为 active=false。**根目录不存在、不可读或为空时直接让本次扫描失败**，不做失效标记。

**匹配规则（Jellyfin 专用，精确匹配，不用 local_organize 的模糊子串）：**

- 关键词范围：`keyword_type = whitelist` 且 `status = active`，用规范名 + 别名构建"归一化文本 → 关键词"字典。
- 本地：先在**原始目录名**上按 `__` 拆段，再逐段用现有 `normalize_keyword_text` 归一化后查字典（归一化会把下划线变成空格，所以必须先拆再归一化）。
- 115：解析 NFO 的全部 `<actor><name>`，逐个查字典；**只要有一个演员命中就不回退**；一个都没命中或 NFO 缺失时，用顶层目录名回退匹配；NFO 解析出错记为 nfo_error，同时仍尝试目录名回退。
- 不处理 merge_policy：目录已由整理脚本按关键词归好，精确匹配不存在"优先 / 兜底"的取舍；兜底词目录照常建合集（见第八节）。

**合集同步：**

- 按媒体库分页拉取 Jellyfin 条目（含 Path），一次性建立"路径 → ItemId"索引，不逐条查询。
- 找不到 ItemId 的条目保持 pending，**不算作"应移除"**；只有 Jellyfin 条目列表完整拉取成功时才执行移除差集。
- 每次修改合集前同时校验数据库映射和合集上的 `18x-managed` 标签；同名手工合集或标签被手工去掉时标为 conflict，只报告不改动。
- 请求设超时；遇到 429 / 5xx 做有限次退避重试；单个合集失败只记录在该合集上，不影响其他合集，也不触发删除。

**调度与并发：**

- 手动触发和每日定时都通过 `BackgroundJobService` 建任务。启动新任务前检查同类型是否已有运行中的任务，有就拒绝；再配合进程内锁。生产是单个 uvicorn 进程，测试用 SQLite，所以不用 PostgreSQL 专用锁。
- 未启用时（开关关闭，或缺少地址 / API Key）不创建客户端、不发任何请求、不启动定时循环，写法参照下载器的开关判断。

**配置：** 多路径配置项沿用 `config.py` 里 `Annotated[list[str], NoDecode]` + `split_csv` 的写法；另加超时、分页大小、定时间隔。

## 七、验收标准

1. Jellyfin 能看到两个媒体库；115 番号条目显示目录里已有的海报和 NFO 信息。
2. Jellyfin 里出现按关键词命名的合集；组合目录里的视频同时出现在对应的几个合集里。
3. 播放验收矩阵全部通过：

   | 场景 | 本地视频 | 115 STRM |
   |---|---|---|
   | 家里网页端 | 能播 | 能播 |
   | 外网网页端 | 能播 | 能播，且确认是 302 到 115（看网络请求或代理日志） |
   | 外网手机客户端（用户常用的一款） | 能播 | 能播，且为 302 |

4. 部署前后对比：Emby 的媒体目录和配置没有任何文件变化；Jellyfin 没有往任何媒体目录写入文件。
5. 第二次运行合集同步时没有多余改动（幂等）；手工建的合集不受影响。
6. 未匹配列表能正确列出匹配不上的路径。

## 八、留给实施者的决定

- 「本地已整理」库的 Jellyfin 库类型（电影 / 家庭视频与照片 / 混合）：以"不联网识别、标题用文件名、按文件夹可浏览"为准，实测后选定。
- 数据表的具体结构与命名、API 路由命名、页面在导航中的位置。
- 新 MediaWarp 实例的镜像版本（建议与现有实例一致）和宿主机端口（不与现有容器冲突）。
- 合集里条目的排序方式。

**已由设计方定下的取舍（用户可推翻）：**

- 「抖音」「抖音风」这类兜底目录照常按关键词建合集，不做特殊处理。
- 第一版不配置硬件转码，以直接播放为准；某客户端需要转码才能播时，记录下来留到后续处理。
- 外网验收用的手机客户端在验收时由用户指定。

## 八之二、主要风险

- **115 直链校验客户端标识**：部分播放器跳转到 115 直链后可能被拒绝或无法拖动进度。验收矩阵会实测；不通过时先调代理配置，仍不行则记录哪些客户端受限。
- **路径对不上**：Jellyfin 和 18x 容器内路径不一致时合集同步会找不到条目，所以两个容器统一使用 5.1 节列出的宿主机原路径。
- **重复条目**：如果误把 `porn_tv1` 也加进 Jellyfin，约 6300 个视频会出现两份。验收时检查库里只有 `302porn_tv1`。
- **Jellyfin 首次扫描耗时长**：约 3.9 万个条目，首次扫描可能要较长时间，期间合集同步只覆盖已扫到的部分。
