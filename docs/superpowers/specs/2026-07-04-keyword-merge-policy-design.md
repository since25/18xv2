# 白名单关键词合并策略设计文档

**日期**：2026-07-04
**作者**：王易川 / Codex
**状态**：设计阶段

---

## 1. 背景与目标

当前整理任务会把同一路径下命中的 2-3 个白名单关键词合并成组合目录，例如 `口巾SANG__露脸_泄密_反差_电报`。这对多个真实主体同时出现的目录有价值，但对“泛化描述类关键词”会产生错误归类。

本次要支持一类低优先级白名单关键词，例如 `露脸_泄密_反差_电报`：

- 当它和任何普通白名单关键词同时命中时，不参与组合目录。
- 当它是该路径唯一命中的白名单关键词时，仍然正常生效。
- 后续可继续新增同类关键词，并能在前端创建和编辑。

目标是把这类规则写入数据库，让整理逻辑、冲突列表、API 和前端维护入口保持一致。

## 2. 非目标

- 不改变关键词命中扫描本身，`keyword_hits` 仍记录所有命中。
- 不删除或重写历史整理任务；新规则在重新生成整理任务时生效。
- 不引入复杂排序模型。当前只需要“普通关键词”和“仅单独命中时生效”两种合并策略。
- 不改变黑名单、忽略词、标签的既有语义。

## 3. 数据模型

在 `keyword_entries` 增加字段：

```python
merge_policy: Mapped[str] = mapped_column(
    String(32),
    nullable=False,
    default="normal",
    server_default="normal",
    index=True,
)
```

取值：

| 值 | 含义 |
|---|---|
| `normal` | 默认策略。参与单关键词整理、组合目录、歧义裁决。 |
| `fallback_only` | 低优先级策略。只有在同一路径没有任何 `normal` 白名单命中时才参与整理。 |

迁移策略：

- Alembic 新增 revision，为 `keyword_entries` 添加 `merge_policy`。
- 现有关键词全部回填为 `normal`。
- 后续可通过前端或 API 把指定关键词改为 `fallback_only`。

## 4. 后端行为

### 4.1 整理任务生成

核心入口是 `OrganizeTaskService.generate_tasks_from_import_hits()`。

新规则在“按路径聚合命中并解析关键词集合”阶段生效：

1. 先沿用现有 `_resolve_specific_keyword_ids()`，处理短别名被长关键词覆盖的情况。
2. 根据解析后的关键词集合读取 `merge_policy`。
3. 如果集合里存在任意 `normal` 白名单关键词，则剔除所有 `fallback_only` 关键词。
4. 如果集合里全是 `fallback_only`，则保留它们，继续走现有单关键词或组合逻辑。

示例：

| 命中集合 | 策略结果 | 目标目录 |
|---|---|---|
| `口巾SANG` + `露脸_泄密_反差_电报` | 保留 `口巾SANG` | `/根目录/已整理/口巾SANG/<原目录>` |
| `露脸_泄密_反差_电报` | 保留该关键词 | `/根目录/已整理/露脸_泄密_反差_电报/<原目录>` |
| `A` + `B` + `露脸_泄密_反差_电报` | 保留 `A` + `B` | `/根目录/已整理/A__B/<原目录>` |
| `fallback_only X` + `fallback_only Y` | 保留 X + Y | 继续按现有组合规则生成 `X__Y` |

### 4.2 歧义冲突列表

`list_ambiguous_conflicts()` 必须使用同一套策略过滤结果。否则前端可能仍把低优先级关键词作为人工裁决选项展示，和自动生成任务不一致。

### 4.3 单关键词生成接口

`generate_tasks_from_keyword_hits(keyword_entry_id=...)` 保持不变。用户明确选择某个关键词生成整理任务时，应尊重用户选择，即使它是 `fallback_only`。

### 4.4 API 和 schema

关键词相关 schema 增加 `merge_policy`：

- `KeywordEntryResponse`
- `KeywordEntryCreate`
- `KeywordEntryUpdate`
- 批量创建/导入如果没有传值，默认 `normal`

后端校验只允许 `normal` 和 `fallback_only`。字段仅对白名单整理有实际影响，但可以在所有 `keyword_entries` 上保留默认值，避免模型分裂。

## 5. 前端设计

### 5.1 维护入口

在关键词管理页面提供“合并策略/优先级”编辑入口：

- 列表中展示当前策略。
- 创建关键词时可选择策略，默认 `普通`。
- 编辑关键词时可修改策略。
- 批量创建白名单时可使用默认 `普通`，无需强制用户逐条配置。

建议文案：

| 后端值 | 前端显示 | 说明 |
|---|---|---|
| `normal` | 普通 | 可参与组合目录 |
| `fallback_only` | 低优先级 | 仅在没有其他普通白名单命中时生效 |

### 5.2 交互约束

- 对非白名单关键词也展示默认值即可，但可以禁用说明文案中的“整理”语义，避免误解。
- 修改策略后提示用户：规则会在重新生成整理任务时生效。
- 不需要新增独立页面；复用现有关键词创建/编辑入口。

## 6. 测试计划

后端单元测试：

- `normal + fallback_only` 只生成普通关键词目录。
- 单独 `fallback_only` 仍生成该关键词目录。
- `normal A + normal B + fallback_only` 生成 `A__B`，不包含低优先级关键词。
- 全部为 `fallback_only` 时仍按现有规则生成单目录或组合目录。
- `list_ambiguous_conflicts()` 不把被普通关键词覆盖的 `fallback_only` 计入冲突选项。
- schema/API 创建和更新能保存 `merge_policy`，非法值返回校验错误。

迁移测试：

- Alembic 升级后 `keyword_entries.merge_policy` 存在且默认 `normal`。

前端测试：

- 关键词列表能渲染策略。
- 创建/编辑表单能提交 `merge_policy`。
- API 类型包含 `merge_policy`。

## 7. 兼容性与风险

- 现有数据库升级后所有关键词默认为 `normal`，行为保持不变。
- 规则只影响整理任务重新生成，不影响历史 `keyword_hits`，可回溯命中原因。
- 如果用户把多个泛化关键词都设为 `fallback_only`，且某路径只命中这些泛化关键词，仍可能生成组合目录。这符合“只有没有普通关键词时才生效”的定义；后续若需要更严格规则，可再增加 `never_combine` 策略。
- 前后端必须同步更新，否则前端无法创建或编辑策略，后端也无法在整理时持久识别低优先级关键词。
