# 女优档案 + 黑白名单 + 115 联动删除 设计

> 日期：2026-11-25
> 状态：已实施（待上线）。用户已批准（2026-11-25）；实施记录见 `progress/2026-11-26-actress-archive.md`，使用说明见 `docs/actresses.md`
> 范围：Jellyfin 联动三段中的第二段。第一段（本地视频显示名）已上线，见 `2026-11-25-jellyfin-display-names-design.md`；第三段（扩展 iOS 播放器 fklema）另行设计，本段只把它要用的后端接口定好。白名单的「搜未入库 + 订阅」放到下一段（本段之后、单独设计）。

## 一、背景与目的

18x 已经把本地「已整理」和 115 番号 STRM（`302porn_tv1`）接进了 Jellyfin，并按关键词建合集（见 `2026-11-01-jellyfin-v1-design.md`）。115 一侧的番号片由 MDC 刮削，NFO 里有完整的演员名单，但 18x 里没有「女优」这个实体：现有黑白名单都挂在关键词上，而且 115 侧的演员目录和现有白名单关键词零重合。

用户希望（2026-11-01 提出方向，2026-11-25 逐条确认）：

- 单独维护一份女优名单，每个人是「黑名单 / 白名单 / 未标」之一；
- **黑名单用来删片**：被拉黑的人的片子，连同 115 原文件一起删掉，Jellyfin 里也随之消失；
- **白名单用来保护和归类**：多人片里只要有白名单的人就不删；白名单的人在 Jellyfin 里有自己的合集；以后（下一段）还要基于白名单做「搜未入库资源 + 订阅」；
- 看片时能在播放器里直接把片中的人标进名单。

## 二、目标 / 非目标 / 反目标

**目标**

1. 18x 新增独立的女优档案：每天从 `302porn_tv1` 的 NFO 自动收录演员，记录状态、别名、标记来源和片数。
2. 拉黑一个人后，自动把「她出演、且片中没有白名单演员」的片子放进删除草稿；用户在网页上确认后，才删除 115 原文件、`porn_tv1` 的 STRM 和 `302porn_tv1` 的番号目录，Jellyfin 条目随后消失。
3. 每天的定时任务发现黑名单女优的新片时，自动追加进删除草稿，等用户确认。
4. 白名单女优在 Jellyfin 里有自己的合集，由现有合集同步一并维护。
5. 提供给播放器（第三段的 fklema）使用的接口：按当前播放的片子查演员及其状态，点一个人直接改状态。
6. 网页上有女优页和删除草稿页。

**非目标（本段不做）**

- 白名单的「搜未入库资源、已入库 / 未入库、订阅」：下一段单独设计，届时参考用户局域网里的 newbyte（8000 端口）和 bytemuse（3750 端口），需要用户在内置浏览器里登录后再调研。本段只保证档案结构能直接被下一段复用。
- 本地「已整理」的删除：那边按关键词整理、与 115 演员零重合，继续由 DEL 脚本 + 普通关键词黑名单负责。
- 没有被 MDC 刮削过的约 1000 个 115 片子（只在 `porn_tv1`、没有 NFO）：没有演员信息，本段找不到。
- 头像、生日、简介等资料的抓取和存储：交给 mdc-ng（它负责写 NFO 和 Jellyfin 人物资料）。
- 播放器里「只删当前这一部」（不拉黑任何人）：设计方决定本段不做，用户可推翻（见第十节）。
- fklema 的界面改动：第三段做。
- Emby 一侧：现有 `emby_blacklist` / `emby_whitelist` 关键词类型、Emby 删除计划表和代码都不动。
- 115 上删完文件后留下的空目录清理。

**反目标（即使能跑也算失败）**

- 没经过网页确认就删除任何文件（包括每日任务发现的新片）。
- 删除了片中有白名单演员的片子。
- 女优名进入普通关键词黑名单 / 白名单，从而影响 DEL 脚本、sehuatang 过滤、下载过滤或本地整理。
- 115 原文件没删成功，却先删了本地 STRM（alist-strm 会按 115 目录重新生成 STRM，MDC 再刮削一遍，片子又回来）。
- 调用 Jellyfin 的「删除条目」接口（它会尝试删媒体文件），或对 Jellyfin 做全量刷新（`FullRefresh` / 替换全部元数据；2026-11-02 曾把服务器负载拉到约 35）。
- 改动本地「已整理」、Emby 的配置和 Emby 自己的整理目录（`mp302_*` 等）、非 18x 管理的 Jellyfin 合集。

说明：如果 Emby 的媒体库也读 `porn_tv1` / `302porn_tv1`，被删的片子在 Emby 下次扫库后也会消失。这是联动删除 115 原文件的必然结果（原文件没了，Emby 里的 STRM 也播不了），不算违反上面一条。18x 不主动触发 Emby 扫库（设计方决定，见第十节）。

## 五、设计

### 5.1 女优档案

每个女优一条档案：

- **名字**：一个规范名 + 若干别名。匹配 NFO 演员名时，用规范名和全部别名，按现有关键词的归一化规则（`normalize_keyword_text`）比较。别名在全部女优之间唯一。
- **状态**：`黑名单` / `白名单` / `未标`，默认未标。
- **标记记录**：每次改状态记一条：改成什么、什么时候、来源（网页 / 播放器 / 导入）、从哪部片上标的（如有）。
- **片数**：每次扫描后统计她在 `302porn_tv1` 里出现在多少个有效番号目录中。

**建档**：每日任务（5.4）把 NFO 里出现、还匹配不到任何档案的名字自动建档为「未标」。

**合并**：MDC 对同一个人可能用不同写法，所以要能「把 A 合并进 B」：A 的规范名和别名都变成 B 的别名，A 的标记记录和片子关联转到 B，A 删除。两人状态冲突（一黑一白）时拒绝合并，提示用户先改状态。合并后对删除草稿重新评估（5.3）。

**头像**：18x 不存。网页需要时，由后端按名字向 Jellyfin 取人物图片并转发给浏览器（浏览器不直接拿 Jellyfin 的 API Key）；取不到就显示占位。

**旧名单导入**：实施时先只读查生产上 `emby_blacklist` / `emby_whitelist` 有多少条。有的话列给用户看，用户同意后一次性导入为对应状态（标记来源记为「导入」）；Emby 的这两种关键词本身不改不删。

### 5.2 片子与演员

- 一部片 = `302porn_tv1` 下的一个番号目录。目录里可能有不止一个 `.strm`（分段 CD1 / CD2），它们同属一部片。
- 片子的演员 = 该目录里 NFO 的全部 `<actor><name>`，按 5.1 的规则对应到档案。
- **只用 NFO 判断演员**。NFO 缺失或解析失败的片子不进入删除候选（演员目录名可能是第一位演员或「多人」，不可靠），只在统计里计数。
- 扫描时保存每个 STRM 条目的演员名单（原样名字 + 归一化名字），每次扫描整体重算，和现有关键词匹配一样不留历史。表结构由实施者定。

### 5.3 删片规则（用户已确认）

一部片 **应删** 当且仅当同时满足：

1. 演员里至少有一个人是黑名单；
2. 演员里没有任何人受白名单保护。**受保护**指：女优档案里是白名单；或者演员名（按归一化规则）等于某个启用中的普通关键词白名单（`whitelist`）或 Emby 白名单（`emby_whitelist`）关键词的规范名或别名。后两种只读不写，保证用户以前放进关键词白名单的人也不会被误删（设计方决定，见第十节）；
3. 没有被用户标为「保留」（见 5.4）；
4. 片子在最近一次扫描中仍有效。

**重新评估时机**：任何人状态变化、合并、每日任务、以及执行前逐部片再判断一次。草稿里不再满足规则的片子自动移出（执行时则跳过，记原因「已受白名单保护」等）。

### 5.4 删除草稿与确认

- **删除草稿是一份持续更新的「待删清单」**：所有当前满足 5.3 规则的片子都在里面。拉黑一个人、每日任务发现新片，都会往里追加；规则不再满足的自动移出。
- 清单按片列出：番号、标题、因为谁（黑名单的人）、同片其他演员及其状态、要删的文件清单（115 原文件、`porn_tv1` STRM、`302porn_tv1` 番号目录）、115 文件当前能否解析到。
- 每部片有三种处理：
  - **本次删除**（勾选框，默认勾选，提供全选 / 全不选）；
  - **不勾选**：这次不删，继续留在清单里，下次再看；
  - **保留**（单独的按钮，可批量）：移出清单并记入保留名单，以后每日任务不再提出它；网页上可以撤销保留。
- 点「确认删除」后，只把**本次勾选的片子**作为一个「删除批次」交给后台任务执行（复用 `BackgroundJobService`，同一时间只跑一个删除任务），逐部片、逐个文件记录结果。任务被中断后可以从未完成的部分继续。没勾选的片子留在清单里不受影响。（2026-11-26 实施时补充：「确认删除」只删网页上当时勾选、并在确认框里看到的那份清单，请求里带上这些番号目录，不按服务端存的勾选标记去删，因为每日任务会往清单里加用户没见过的默认勾选新片；这份清单里有片子已不在待删清单里、或确认框打开期间清单有变化时，提示「清单有变化，请刷新后再确认 / 请重新确认」，一部都不删。）
- 每日任务追加新片后，不发通知，用户下次打开草稿页时看到（通知方式留到以后需要时再加）。

### 5.5 删一部片的执行顺序

对每部勾选的片子，按以下顺序执行；**前一步失败就停在这部片**，记失败原因，继续下一部：

1. **再判断一次 5.3 的规则**，不满足就跳过。
2. **解析 115 文件**：读番号目录里每个 `.strm` 的地址，用 `decode_115_open_path` 得到 115 路径，再用 `get_file(path=...)` 拿 file_id。115 上已经找不到的，记为「115 已不存在」，视为这一步成功。
3. **删 115 原文件**：`delete_node(file_id)`。实施时先核实 115 开放接口的删除是否进回收站（预期是，可在 115 回收站找回）。
4. **删 `porn_tv1` 里对应的 STRM**：按 STRM 地址在 `porn_tv1` 里找内容相同的 `.strm`（不依赖硬链接或 inode）。为避免逐部片全目录搜索，同一次执行先建一次「地址 → 路径」索引。
5. **删 `302porn_tv1` 的番号目录**（`.strm`、`.nfo`、图片整个目录）。删完后，演员目录如果变空，只删这个空目录，不往上递归。注意：现有 `PathGuard.delete_path` 拒绝删目录（`directory_delete_not_allowed`），需要扩展为「只允许删 `302porn_tv1` 下恰好两层深的番号目录，以及变空的演员目录」，其他目录仍然拒绝。
6. **在 18x 里把这部片的条目标为失效**，让片数和草稿立刻更新。

本地删除只允许落在 `porn_tv1` 和 `302porn_tv1` 两个根目录内（复用 `PathGuard`）。扫描得到的路径是只读挂载的 `/mnt/user/docker1/alist-strm/video/...`，删除时换成可写挂载的 `/mnt/cache/docker1/alist-strm/video/...`；这个换算做成配置项。上线前要只读核实两个路径看到的是同一批文件（同一文件的 inode 一致），核实不通过就改为调整容器挂载，由用户批准。

**Jellyfin 条目**：整份草稿执行完后，触发 Jellyfin 对「115 番号」库的一次普通扫描，让已删的条目消失；如果只能通过全量刷新做到，就不触发，等每天的定时扫库。

### 5.6 每日任务

在现有每日链（扫描 → 合集同步 → 显示名同步）中，扫描之后增加一个女优步骤（任务类型如 `actress:refresh`）：

1. 用本次扫描得到的演员名单更新档案：新名字建档、更新片数。
2. 按 5.3 重新评估：把新出现的应删片子追加进待删清单，把不再应删的移出。

白名单合集放在合集同步步骤里一起做（5.7），所以女优步骤要排在合集同步之前。整个功能由一个总开关控制，默认关闭，关闭时不跑任何女优步骤、不建草稿。

### 5.7 白名单合集

- 每个白名单女优一个 Jellyfin 合集，名字用规范名，带 `18x-managed` 标签，成员是她出演的、已在 Jellyfin 找到条目的有效片子。
- 由现有合集同步一并维护，规则与关键词合集一致：增量增删、只动自己建的合集、单个合集失败不影响其他。
- 移出白名单（或被合并删除）后，她的合集清空并删除（只限 18x 建的）。
- 与已有关键词合集重名时，标为冲突、只报告不改动。

### 5.8 接口草案（路由名由实施者定）

给网页和播放器共用，沿用 18x 现有登录鉴权（fklema 已会登录 18x）：

- **女优列表**：按状态筛选、按名字搜索、按片数排序、分页。
- **女优详情**：名字和别名、状态、标记记录、她的片子（每部片带同片演员及状态、是否受保护）。
- **改状态**：设为黑 / 白 / 未标，带来源（网页 / 播放器）和可选的片子引用；返回新状态，以及对草稿的影响（如「已放进删除草稿 12 部」「草稿移出 3 部」）。支持批量。
- **别名**：增、删；合并。
- **头像**：按女优转发 Jellyfin 人物图片。
- **按片查演员**（给播放器）：传 Jellyfin 条目 ID 或媒体路径，返回这部片的演员列表、各自状态、这部片是否在草稿里。用 Jellyfin 条目 ID 查时，通过扫描表里已有的 `jellyfin_item_id` 对应到片子。
- **删除草稿**：查看待删清单、勾选 / 取消勾选、标为保留、确认删除（只执行勾选的）、查看执行进度和逐项结果、历史删除批次、保留名单及撤销保留。

## 六、验收标准

1. 开启后跑一次每日任务：档案里出现 NFO 中的演员，状态都是未标；抽查几个人的片数与 `302porn_tv1` 实际一致。
2. 网页拉黑一个人：草稿里出现她的片子；有白名单同片演员的片子不在草稿里；每部片显示原因和同片演员。
3. 通过「改状态」接口（模拟播放器）拉黑：效果与第 2 条相同，标记记录里来源为播放器、带片子引用。
4. 把一个同片演员加白：草稿里对应的片子自动移出。同片演员是普通关键词白名单里的名字时，片子同样不进清单。
5. **首次真实删除只删 1 部用户指定的片子**（清单里只勾这一部）：115 原文件消失（并核实能在 115 回收站看到）、`porn_tv1` 的 STRM 和 `302porn_tv1` 的番号目录消失；Jellyfin 普通扫库后条目消失；对比执行前后，`porn_tv1` / `302porn_tv1` 中只有这部片相关的文件变化，本地「已整理」和 Emby 自己的整理目录（`mp302_*` 等）没有变化；没勾选的片子仍在清单里。
6. 把一部片标为保留：它移出清单、进入保留名单，第二天的每日任务不再把它放回清单；撤销保留后它回到清单。
7. 黑名单女优有新片被刮削进来（测试里用夹具模拟）：下一次每日任务后它出现在草稿里，未经确认不会被删。
8. 115 删除失败时（测试里用假客户端模拟）：这部片的本地 STRM 和番号目录都还在，记为失败，可以重试。
9. 加白一个人：Jellyfin 出现她的合集；移出白名单后合集被删除；手工合集和关键词合集不受影响。
10. 普通关键词黑名单 / 白名单、DEL 脚本导出的关键词文件内容不因本功能变化。

测试按项目约定在 Spark 上跑（`scripts/remote-test.sh`），文件系统和 115、Jellyfin 都用夹具和假客户端。

## 七、风险

- **路径换算不成立**：如果 `docker1` 共享有一部分文件不在 cache 上，`/mnt/cache/...` 看不到它们，删除会找不到文件。上线前只读核实；不成立就改挂载。
- **删了又回来**：OpenList 有目录缓存，alist-strm 可能在缓存刷新前按旧列表重新生成 `porn_tv1` 的 STRM，MDC 再刮削一遍。此时 115 文件已不存在，每日任务会把它再次放进草稿，确认后只删本地文件，能自愈；首次真实删除时观察一天确认。
- **MDC 写法不一**：同一个人在不同片里名字写法不同，拉黑后会漏片。靠合并和别名解决；女优详情里能看到「她的片子」，便于发现漏的。
- **115 风控**：一次拉黑多产的人可能一次删上百个文件。115 客户端自带限速；执行任务按顺序逐个删，不并发。
- **115 回收站假设**：若 115 开放接口删除不进回收站，删除就不可找回；实施时先核实，再决定是否在确认按钮上加更强的提示。

## 十、设计方已做的决定（用户可推翻）

- 演员只看 NFO，不用演员目录名回退；NFO 缺失的片子不进删除候选。
- 删除草稿是一份持续更新的待删清单；每次确认只执行勾选的片子，没勾选的留在清单里；「保留」是单独的操作（2026-11-25 审阅后修改：原先「取消勾选 = 永久保留」会让「只删一部」变得很麻烦）。
- 「受白名单保护」除了女优档案的白名单，也包括 NFO 演员名命中的普通关键词白名单和 Emby 白名单（只读）。宁可少删，不误删。
- 18x 不主动触发 Emby 扫库；片子在 Emby 里随 Emby 自己的扫库消失。
- 演员目录删空后顺手删掉这个空目录；115 上的空目录不处理。
- 每日任务追加新片不发通知。
- 本段不做「播放器里只删当前这一部」。
- 白名单合集用女优规范名命名，与关键词合集重名时只报告冲突。
- 合并时两人状态冲突就拒绝合并。
