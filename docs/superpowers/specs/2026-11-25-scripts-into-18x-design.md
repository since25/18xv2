# 阶段 7：Unraid 三个定时脚本搬进 18x 设计

> 日期：2026-11-25
> 状态：待用户批准（问题已全部答复）
> 范围：`sehuatang`、`MOVE_SSD_CACHE_TO_DISK2`、`DEL_SOMETHING` 三个脚本改由 18x 执行、调度、监控和调参。Unraid 上其他 User Scripts 不动。
> 前置：阶段 6「脚本日报」（`docs/superpowers/specs/2026-11-02-script-run-reports-design.md`）已上线，本阶段在它的基础上扩展，并推翻其中“不由 18x 接管执行”这条非目标。

## 一、背景与目的

现在这三个脚本由 Unraid 的 User Scripts 插件按时触发。用户要运行、看日志、改时间，都得进 Unraid 主页 → 设置 → User Scripts 去点；改参数要 SSH 上去改 `/boot` 下的文件或 Python 源码。阶段 6 已经让两个脚本把结果回报给 18x，但执行仍在 Unraid，sehuatang 也还没有任何总结。

用户要的是：**三个脚本都在 18x 里管理——能执行、能监控、能看日志、能调参数**，不再依赖 User Scripts 插件。

现状（2026-11-25 只读核对）：

| 脚本 | 定时 | 实际做什么 | 现有监控 |
|---|---|---|---|
| `sehuatang` | 每天 01:28，约 6 分钟 | 壳脚本调用 `PYTHON_SEHUATANG/gc.py`：抓论坛列表前 4 页，按 `blacklist.txt`（8 个 AI 词）过滤标题，进帖子把磁力推给 qB（分类「国产BT」），并把种子文件存进 `torrents/`。qB 容器把该目录挂成监视目录，自动取走。每天另写一个 CSV（已积 217 个） | 无 |
| `MOVE_SSD_CACHE_TO_DISK2` | 每天 01:01 | bash 脚本，把 `SSD_cache/已整理` 合并搬到 `disk2/qbbtdn/已整理`，最后修正权限 | 阶段 6 日报 |
| `DEL_SOMETHING` | 每天 12:09 | bash 外壳，调用 `delsomethin/delete_files.py`（按 18x 黑名单删），再按 7 条“扫描目录 → 目标目录”调用整理脚本（按 18x 白名单归类），最后 `chown -R` 修正权限 | 阶段 6 日报 |

`gc.py` 里写着 qB 账号密码和站点 cookie 明文；两个整理脚本 `local_organize_from_whitelist.py` 和 `_telegram.py` 除了默认扫描目录和一行注释，内容相同。

## 二、目标 / 非目标 / 反目标

**目标**

1. 三个脚本在 18x 容器里运行，由 18x 按时触发，也能在页面上手动“立即运行”“演练运行”和“停止”。
2. 运行时能在页面上实时看日志，历史日志保留 30 天。
3. 每次运行都有总结和名单（DEL、MOVE 沿用阶段 6 的统计；sehuatang 新增），到点没跑仍然提醒。
4. 时间、开关和第四节列出的参数都在页面上调整，不用再进 Unraid。
5. sehuatang 标题改用 18x 黑名单过滤，种子先检查再通过 qB 接口提交。

**非目标**

- 改变 DEL、MOVE 删什么、搬什么、归到哪的判定规则。
- 搬迁 Unraid 上其他 User Scripts，以及 `dedup.py`、`DELDIR.py`、`98t.py` 等不在定时里的脚本。
- 主动推送提醒（仍然只在页面里看）。
- 导入 sehuatang 历史 CSV。
- 单独的“干活容器”（见第三节方案 C，留作以后的升级路线）。

**反目标（即使能跑也算失败）**

- 同样的目录和关键词，18x 版 DEL / MOVE 的删除、移动结果与 Unraid 版不一致。
- 跑任务时 18x 网页明显变慢或卡住。
- qB 密码、站点 cookie 出现在页面、日志、仓库或运行记录里。
- Unraid 和 18x 在同一天各跑一次同一个脚本。
- 部署或重启打断任务后，页面看不出来。

## 三、做法（用户已选 A）

| 做法 | 说明 | 取舍 |
|---|---|---|
| **A 直接在 18x 容器里跑（已选）** | 18x 到点起子进程运行脚本，日志边跑边存，跑完直接写库 | 最简单，只有一个容器、一套部署，照搬 Jellyfin 每日任务的写法；代价是部署 18x 会打断正在跑的任务，18x 容器要挂上媒体目录、拿到删改权限，任务和网页共用内存 |
| C 另起一个“干活容器” | 同一套代码多起一个容器专门跑脚本，网页只下指令 | 隔离更好，可以单独限制内存；但多一个容器要部署和看护，指令要经数据库排队传递，工作量大约多三成 |
| B 18x 用 SSH 遥控宿主机执行 | 脚本环境和现在完全一样 | 18x 要持有 Unraid 的 root 钥匙，一旦被攻破就是整台服务器的风险；代码仍在宿主机上，没解决“代码不进仓库” |

选 A 的理由：用户要的是在一个地方管理，A 改动最少，也和一期把监控搬进 18x 的思路一致。以后如果发现任务和网页抢资源，可以平移成 C，页面和脚本代码不用重写。

6. sehuatang 不再每天写 CSV，明细进库。

## 五、整体结构

```
18x 容器（root 运行）
  ├─ 调度循环（lifespan 里一个协程，每分钟检查一次）
  │     └─ 到点且今天还没跑 → 创建运行记录 → 启动子进程
  ├─ 子进程（python / bash，与网页进程隔离）
  │     ├─ sehuatang：仓库内新模块，直接写结构化结果
  │     ├─ MOVE：仓库内 bash 脚本，原逻辑
  │     └─ DEL：仓库内 Python 编排 + 原 delete_files.py / 整理脚本
  ├─ 日志文件 data/script-logs/<脚本>/<运行ID>.log（边写边可读）
  ├─ 跑完：解析输出（DEL、MOVE 复用阶段 6 的解析）→ script_runs / script_run_items
  └─ 页面「脚本中心」（由现在的「脚本日报」页扩展而来）
```

## 六、各部分设计

### 1. 调度与执行

- 每个脚本一条配置记录（见第 7 小节），包括开关、运行时间（Asia/Shanghai）和参数。
- 调度协程每分钟检查一次：已启用、执行方为 18x（见第 7 小节）、已过当天运行时间、今天的**定时运行**还没完成，就启动一次。
- **“今天的定时运行已完成”的判断（我的决定）**：今天有一条由定时触发的非演练记录，且状态是成功、警告、失败、超时或被用户停止。具体规则：
  - **手动运行不算**：上午手动真实跑过 DEL，12:09 的定时照常跑。
  - **失败不自动重试**，避免反复冲击站点或磁盘。
  - **“中断”不算完成**：部署或重启打断的那次，在下面的补跑窗口内会再跑一次。
- **补跑（我的决定）**：18x 在预定时间停机或中断了任务，恢复后如果离预定时间不到 2 小时，就补跑；超过 2 小时不补跑，页面显示“今天没有运行记录”。
- 子进程与网页进程分开，网页接口不等子进程。标准输出和错误输出合并，逐行写进日志文件。
- **互斥（我的决定）**：同一个脚本同时只能跑一次。DEL 和 MOVE 都会动 `SSD_cache/已整理`，两者也互斥，后到的排队等待，不跳过。sehuatang 不受影响。
- **停止**：先发 SIGTERM，30 秒后仍未退出再发 SIGKILL，状态记为“已停止”。
- **中断**：18x 启动时把仍标记为“运行中”的记录改成“中断”，页面上明确显示。
- **超时（我的决定，先给默认值）**：sehuatang 1 小时，MOVE 6 小时，DEL 3 小时。超时按“停止”处理并记为失败。
- **演练**：DEL、MOVE 用它们原有的演练开关（`DRY_RUN` / `--dry-run`）；sehuatang 演练时照常抓取和过滤，但不提交 qB、不记“已提交”。演练记录会显示，但不计入趋势图，也不算“今天已运行”。

### 2. 目录挂载与权限

`docker/docker-compose.yml` 给 app 容器新增：

| 宿主机路径 | 容器内路径 | 用途 |
|---|---|---|
| `/mnt/cache/docker1/SSD_cache` | 相同 | DEL 删除和整理、MOVE 的源目录 |
| `/mnt/disk2/qbbtdn` | 相同 | DEL 删除和整理、MOVE 的目标目录 |

- 现有的 `/mnt/disk2/qbbtdn/已整理` 挂载被新挂载覆盖，Jellyfin 封面功能使用的路径不变。
- 2026-11-25 已核对，现有路径全部在这两个根之下，并且都是磁盘路径，不经过 `/mnt/user` 共享：
  - 删除扫描目录（`target_dirs.csv`）：`/mnt/cache/docker1/SSD_cache/`、`/mnt/disk2/qbbtdn/00000000000000000/scripts`、`/mnt/disk2/qbbtdn/已整理`。
  - 7 条整理任务：扫描目录是 `SSD_cache` 下的 `finish`、`telegram`、`已整理/抖音`、`已整理/抖音风`，以及 `disk2/qbbtdn` 下的 `00000000000000000/scripts`、`已整理/抖音`、`已整理/抖音风`；目标目录是 `SSD_cache/已整理` 或 `disk2/qbbtdn/已整理`。
  - MOVE：从 `SSD_cache/已整理` 到 `disk2/qbbtdn/已整理`。
  - 例外：`delete_files.py` 的备份目录（`enable_backup=False`，不启用），以及两个日志文件路径，见第 3 小节。
- 容器内路径与宿主机保持一致，页面上的目录、运行名单和阶段 6 的记录可以直接对照。
- **权限必须写成数字 `99:100`**。Unraid 的 `nobody:users` 是 99:100，但容器（Debian）里的 `nobody` 是 65534。照抄 `chown nobody:users` 会把整棵媒体树的归属改错。MOVE 脚本里同样的写法也要一起改。
- 页面上可选的目录只能在这两个挂载根之下，后端保存参数时校验。

### 3. 脚本代码进仓库

- 放在 `scripts/jobs/`（具体目录结构由实施者定），随 18x 镜像一起部署。
- **源码来源**：仓库里目前没有这些脚本。实施第一步由主会话通过只读 SSH 从生产机复制：
  - `/mnt/cache/docker1/python/scripts/delsomethin/` 下的 `delete_files.py`、`local_organize_from_whitelist.py`、`target_dirs.csv`；
  - `/boot/config/plugins/user.scripts/scripts/` 下的 `DEL_SOMETHING/script`、`MOVE_SSD_CACHE_TO_DISK2/script`；
  - `/mnt/user/docker1/python/scripts/PYTHON_SEHUATANG/` 下的 `gc.py`、`blacklist_filter.py`。

  复制进仓库前先去掉凭证：`gc.py` 里的 qB 账号密码和站点 cookie 不进仓库，sehuatang 是重写，只参考它的抓取逻辑；DEL 的 `.env` 不复制。
- **已核对的现有开关**：
  - `delete_files.py` 和整理脚本都读环境变量 `DRY_RUN`，演练模式不删除也不移动。
  - 整理脚本读 `ORGANIZE_SCAN_ROOT`、`ORGANIZE_TARGET_ROOT`、`MERGE_ON_CONFLICT`（同名目录合并），`delete_files.py` 读 `TARGET_DIRS_CSV`。
  - 两者都需要 `KEYWORDS_API_USERNAME` / `KEYWORDS_API_PASSWORD`，用来登录 18x 取关键词。
  - “修正权限”目前写在 DEL 的 bash 外壳里，没有开关，搬过来后由编排代码按配置决定做不做。
  - 第三方依赖只有 `requests`，18x 已经安装。
- **已核对的取词方式**：脚本分页调用 `GET /api/keywords`，先按类型（删除取 `blacklist`，整理取 `whitelist`）和 `active` 状态过滤，再把别名一并加入（`include_aliases=True`），过滤掉短于 2 个字的词，最后在目录名或文件名里做子串匹配（`fuzzy_match=True`）。
- **DEL**：bash 外壳里的流程（先删除，再按清单逐条整理，最后修正权限）改用 Python 编排；`delete_files.py` 和整理脚本保持原判定逻辑。两个整理脚本合并成一份，扫描目录通过环境变量传入，现在的 bash 外壳也是这样传的（我的决定）。
- 脚本里写死的日志路径（`delete_log.txt`、`local_organize_log.txt`）和 `target_dirs.csv` 改为由 18x 传入，日志统一放到 `data/script-logs/`，扫描目录来自页面配置。
- DEL 现在通过 HTTP 登录 18x 接口取关键词。容器内可以改为读本机接口或直接读库，由实施者定，前提是**取到的词和匹配方式完全不变**（含别名、最短词长 2、子串匹配）。
- **MOVE**：bash 脚本原样进仓库，只改两处：源 / 目标目录由参数传入，权限改成数字。
- 输出格式保持不变，阶段 6 的解析器（现 `scripts/unraid/report_script_run.py` 中的解析部分）移进 `app/`，由执行器直接调用。不再需要回报这一步。

### 4. sehuatang 新流程

1. 按配置抓列表页（页数、版块地址），沿用现有的安全验证页处理（safeid）和随机等待。
2. 标题用 **18x 黑名单**（启用的词条和别名）过滤，匹配方式与 DEL 相同：去掉半角、全角空格，转小写，子串包含，最短词长 2。命中的记录标题和命中词，不进帖子。
3. 帖子编号（URL 里的 tid）以前已经成功提交过的，跳过。只对“已提交”去重，被过滤的帖子每天仍按最新黑名单重新判断。
4. 进帖子取种子附件和磁力。
5. 有种子文件时，解析种子里的文件和目录名，再用黑名单过一遍，命中就不提交。只有磁力时跳过这一步。
6. 通过 qB 接口提交到配置的分类。有种子用种子，没有种子才用磁力，同一帖不两样都提交。不写 qB 监视目录。
   - 2026-11-25 已核对：qB 的「国产BT」分类和监视目录都没有设置单独的保存路径、标签或暂停，都落在 qB 的默认保存路径。
   - 现在磁力先于种子以「国产BT」分类提交，同一个 hash 实际都走这个分类。
   - 所以接口提交只需要带分类，不额外指定 `savepath` 或标签。下载、MOVE、DEL 这条链路不变。
7. 写库：本次总结和每个帖子的去向。

**总结计数**：列表页成功 / 失败数、抓到帖子数、标题被拦数、种子内容被拦数、跳过（已提交过）数、提交成功数、提交失败数。

**名单类别**：已提交、标题被拦（含命中词）、种子被拦（含命中词）、提交失败、帖子解析失败。

**cookie 失效判断**：所有列表页都失败，或遇到 Cloudflare 挑战，或一个帖子都没抓到，就把本次标记为失败，原因写“站点 cookie 可能失效”，页面顶部显示红条，直到下一次成功运行。

**cookie 和 User-Agent**：`cf_clearance` 与浏览器的 User-Agent 绑定，所以页面要能同时更换 cookie 和 User-Agent。两者保存在 `data/` 下的文件里（和 115 cookie 的存法一致），页面只显示“最后更新时间”和是否已设置，不回显内容。

**新表 `sehuatang_posts`**：`tid`（唯一）、标题、帖子地址、首次看到时间、最后结果、最后运行 ID、提交时间。用于去重和查询某帖的去向。

**首次运行去重（我的决定）**：
- 现在的 `gc.py` 本身不去重，靠 qB 拒收已经存在的 hash；qB 里已经删掉的任务会被重新下载。
- 切换时一次性导入最近 14 天 CSV 里出现过的帖子地址，从中取出 tid，标记为“已提交（迁移导入）”。这些 CSV 在 `PYTHON_SEHUATANG/` 下，只读取。
- 这只是为了去重，不是第二节非目标里的“导入历史 CSV”：不导入标题和资源明细，不生成运行记录。

### 5. 8 个 AI 词并入 18x 黑名单

- 并入的词：`AI增强`、`AI增強`、`AI強化`、`AI强化`、`AI放大`、`AI修复`、`AI修復`、`AI生成`。规范名和别名的分组由实施者按现有关键词规则定，`note` 写“来源：sehuatang 标题黑名单，2026-11 合并”。
- 一加入，现在还在 Unraid 上跑的 DEL 下一次（12:09）就会用这 8 个词删文件。所以**加词前**要先做一次只读预估：在 DEL 的 3 个删除扫描目录里，找出名字含这 8 个词的目录和文件，列给用户看，用户确认后才加词。
- 加词操作通过 18x 关键词接口或页面完成，留下操作日志，不直接改库。
- **加词也会影响 18x 里其他读黑名单的功能**（已核对代码）：
  - 下载器同步（`app/services/downloader/sync_service.py`）：标题含这些词的资源，不再生成下载候选。
  - 本地清理（`app/services/cleanup/local_cleanup_service.py`）：用户手动执行清理时，会把这些词算进去。
  - 复核收件（`review_intake`）：只做分类，不受影响。

  用户已确认（2026-11-25）：接受，下载器同步和本地清理也一起拦这 8 个词。加词前的只读预估只覆盖 DEL 的删除目录，因为下载器少生成的候选不会删除任何已有文件。

### 6. 运行记录与日志

- 复用阶段 6 的 `script_runs`、`script_run_items`，新增字段：`trigger`（定时 / 手动）、`dry_run`、`log_path`、`error_reason`。`status` 增加 `running`、`stopped`、`interrupted`。
- `run_key` 继续保证唯一：由脚本名和开始时间组成。
- 名单保留 90 天、上限 5000 条，规则沿用阶段 6。日志文件保留 30 天，每天清理一次。
- 实时日志：页面按字节偏移轮询读取增量（例如每 2 秒一次），运行结束后停止轮询。不引入 WebSocket。
- 日志和名单里不能出现 cookie、密码。sehuatang 打印请求地址时去掉查询串里的敏感参数；qB 报错只记状态码和简短原因。

### 7. 配置存储

- 新表 `script_job_configs`：`job_name`（唯一）、`executor`（`unraid` / `18x`）、`enabled`、`run_time`（HH:MM）、`params`（JSON）、`updated_at`。
- 首次迁移时写入与 Unraid 现状完全一致的默认值，三个脚本的 `executor` 都是 `unraid`，切换时逐个改成 `18x`（见第七节）。
- **执行方为 `unraid` 时（切换前，我的决定）**：
  - 18x 不定时运行，但允许手动演练，用来做对比。
  - 继续接收阶段 6 的回报。
  - 按 `run_time` 检查漏跑，阶段 6 的提醒不中断。sehuatang 切换前没有回报，所以不检查。
  - 卡片上显示“由 Unraid 运行”。
- **执行方为 `18x` 时**：按 `enabled` 定时运行。停用后卡片显示“已停用”，不再提示漏跑。
- 阶段 6 的配置项 `SCRIPT_REPORT_SCHEDULES` 不再使用，运行时间统一由这张表管理。
- `.env` 新增 qB 地址、账号、密码三项。站点 cookie 和 User-Agent 不放 `.env`，见第 4 小节。
- 参数修改写入 `keyword_operation_logs` 风格的操作日志，或者单独记一张修改记录，由实施者定，至少要能查到谁在什么时候把什么参数从什么改成了什么。

## 七、切换步骤（逐个脚本，按 sehuatang → MOVE → DEL 的顺序）

每个脚本都按同样的流程切换：

1. 部署 18x 新版本，这个脚本的执行方仍是 `unraid`。
2. 在 18x 里演练运行，和 Unraid 版同一天的结果对比。
3. 用户确认后：先在 Unraid 上把这个脚本的定时改成 disabled（用户自己点，或经批准由我改 `schedule.json` 并刷新 cron），再在 18x 里把执行方改成 `18x` 并启用。
4. 观察 18x 定时跑完第一次，核对总结和日志。
5. `/boot` 下的原脚本保留，作为回退。

额外步骤：

- **sehuatang**：切换前先完成第六节第 5 小节的加词预估和加词。第一次演练时，页面要列出被 18x 黑名单拦下的标题，供用户检查有没有误拦。
- **MOVE**：演练输出与 Unraid 版 `--dry-run` 的输出逐行比较，应该一致。
- **DEL**：演练输出与 Unraid 版 `DRY_RUN=true` 在同一时刻的输出比较，删除和移动名单应该一致。切换后，阶段 6 插在 `/boot` 脚本里的回报片段和 `delsomethin/report_script_run.py` 随原脚本一起停用。

## 八、验收标准

1. 解析和执行测试：用虚构路径的夹具覆盖 DEL / MOVE 的现有输出，解析结果与阶段 6 一致。
2. sehuatang 测试：用本地假页面和假 qB 覆盖标题被拦、种子内容被拦、已提交跳过、只有磁力、cookie 失效、提交失败等情况。不访问真实站点。
3. 调度测试：到点启动、当天不重复、2 小时内补跑、超过 2 小时不补跑、DEL 和 MOVE 互斥排队、停止、超时、重启后标记中断。
4. 权限测试：修正权限用的是 99:100。
5. 安全测试：日志、接口返回、运行名单里不含 cookie 和密码；未登录访问被拒绝；参数目录不在挂载根下时保存失败。
6. 生产演练对比（第七节第 2 步）一致。
7. 跑任务期间打开网页，页面能正常响应。
8. 用户在页面上确认。

测试在 Spark 上运行：`scripts/remote-test.sh`。

## 十、主要风险

| 风险 | 处理 |
|---|---|
| 部署 18x 打断正在跑的 DEL / MOVE，留下搬了一半的目录 | MOVE 和整理脚本本身逐项处理、可以重跑；页面标记“中断”；部署前检查有没有任务在跑（写进部署说明） |
| 8 个 AI 词误删本地文件 | 加词前做只读预估并由用户确认；DEL 切换前做演练对比 |
| 两字短词误拦 sehuatang 标题（近 7 天 235 个标题中，有 17 个只因两字词被拦） | 每次运行名单列出被拦标题和命中词；用户发现误拦就在关键词页调整 |
| 18x 容器拿到媒体目录的删改权限 | 只挂两个必需的根目录；页面参数限制在挂载根之内；接口仍需登录 |
| 任务和网页抢内存（11-02 有过整机卡死，根因未定） | 子进程独立；sysmon 记录可以对照；资源不够时升级到方案 C |
| cf_clearance 在容器出口 IP 上失效 | 容器和宿主机共用同一个公网出口，预期不受影响；第一次演练就能验证，失效时页面换 cookie |
| 迁移后 Unraid 和 18x 同一天都跑 | 切换步骤规定先停 Unraid 定时再启用 18x；18x 默认停用 |

## 十一、需要用户单独批准的操作

1. 生产数据库迁移（新表、新字段）。
2. 修改 `docker/docker-compose.yml` 的挂载并部署 18x。
3. 往生产 18x 黑名单加入 8 个 AI 词（在只读预估之后）。
4. 每个脚本在 Unraid 上停用定时、在 18x 上启用。
5. 在生产上做真实（非演练）的手动运行。

## 十二、回滚

- 单个脚本：在 18x 里停用，在 Unraid 上恢复定时，`/boot` 原脚本仍可用。
- 8 个 AI 词：在关键词页把这些词条停用。
- 18x 整体：回退版本；新表不影响其他功能，需要时用迁移回退删除；挂载恢复原样。
