# 前后端类型自动生成 设计

日期：2026-11-17
状态：用户已选定“做法二”，待确认本设计

## 意图

前端有 143 个手写的数据类型（`frontend/src/api/` 下 8 个文件），全靠人工与后端保持一致。后端改了字段而前端没跟上时，没有任何检查会报错，只会在页面上表现为内容缺失或出错。目标是让“后端写明了返回内容”的那部分类型由后端定义自动生成，并且后端一改、忘了重新生成时测试会报错。

## 现状

- 后端约 157 个接口，约 105 个写明了返回内容（`response_model` 或返回值标注为数据模型），可以生成。
- 约 50 个接口返回的是没有说明的字典（下载器 16 个、白名单批处理 7 个、文件去重 6 个为主），生成出来只是“任意对象”，没有用。
- 没有核对过两边类型目前是否已经不一致。

## 目标

- 一条命令生成前端类型文件；生成结果入库。
- 后端接口定义变了但没重新生成时，测试失败并提示该运行哪条命令。
- 能由生成得到、且替换后页面代码不需要改的手写类型，改为引用生成的类型；对外的类型名字不变，页面文件不用改。
- 替换过程中发现的两边不一致，逐条列出交用户决定。

## 不做的事

- 不改后端任何接口的行为、返回内容和数据模型（包括不给那约 50 个接口补返回说明，那是“做法三”，以后单独做）。
- 不改页面文件（`frontend/src/pages/`）的逻辑。
- 不生成请求函数，只生成类型；`api/client.ts` 和各 `api/*.ts` 里的请求函数照旧。
- 不拆分页面。

## 不能出现的结果

- 为了让类型对上而修改后端模型或页面逻辑。
- 为了通过编译而加 `any`、`as unknown as`、`@ts-ignore`、`eslint-disable`。
- 生成的类型比手写的宽松（例如后端是普通字符串，前端手写的是几个固定取值）时，仍然替换导致前端失去原有的检查。这种情况保留手写并列入汇报。
- 删除或放宽现有测试。

## 考虑过的做法

1. **只装工具和检查，不替换**。改动最小，但手写的那份仍在，问题没解决。
2. **工具 + 替换能生成的部分（采用）**。只动前端和脚本，不改后端行为。
3. **先给约 50 个接口补返回说明，再全部生成**。最彻底，但要改后端；漏写字段会让该字段从返回里消失，测试不一定发现。留待以后。

## 设计

### 生成链路

```
后端应用定义 ──(导出)──> frontend/openapi.json ──(生成)──> frontend/src/api/schema.gen.ts
```

- `scripts/export_openapi.py`：导入后端应用，把接口定义（`app.openapi()`）按键排序、固定缩进写到 `frontend/openapi.json`。不启动服务、不连数据库、不读 `.env` 里的真实凭证。
- 生成器自写，不新增依赖（2026-11-17 实施中修订）：原定的 `openapi-typescript` 只支持 TypeScript 5，本项目是 TypeScript 6，不强装就装不上。改为在 `scripts/export_openapi.py` 里用 Python 直接把 `openapi.json` 的数据模型部分（`components.schemas`）写成 `src/api/schema.gen.ts`，导出 `components` 接口。只需要数据模型，不需要接口路径。遇到不认识的定义写法时直接报错退出，不猜测、不输出宽松类型。
- 带默认值的返回字段按必填生成（2026-11-17 第二轮修订）：后端导出的接口定义把带默认值的字段一律标成可选，但返回数据时这些字段一直都在（全仓没有使用 `exclude_unset` / `exclude_none` / `exclude_defaults`）。生成器因此区分用途：**只出现在返回内容里**（含被返回模型间接引用）的数据模型，所有字段都生成为必填（最初只处理定义中带 `default` 的字段，但 `X | None = None` 和 `default_factory` 的字段在导出的接口定义里没有 `default`，而返回时同样一直都在，所以改为不看 `default`）；出现在请求参数或请求体里的模型（包括两边都用到的）维持原样。后端数据模型有 190 个、分散在 27 个文件且没有共同基类，所以不在后端改配置，`app/` 仍然不动。
- `scripts/gen-api-types.sh`：一条命令完成全过程。因为本机不跑 Python 测试环境，它在 Spark 上执行导出和生成，再把 `frontend/openapi.json`、`frontend/src/api/schema.gen.ts` 取回本机。
- 两个生成文件都入库。`schema.gen.ts` 不参与 lint（在 eslint 配置里忽略该文件）。

### 自动检查

- 后端测试 `tests/api/test_openapi_snapshot.py`：当前应用的接口定义与入库的 `frontend/openapi.json` 不一致时失败，报错信息写明“运行 `scripts/gen-api-types.sh` 重新生成”。
- 同一个后端测试文件里再加一项：重新生成的类型内容与入库的 `schema.gen.ts` 不一致时失败（生成器在 Python 一侧，所以检查也放在后端测试里）。
- 生成器本身有单元测试，覆盖必填与可选字段、可空、数组、引用、固定取值、字典等写法，以及“不认识的写法报错”。
- 都随现有的 `scripts/remote-test.sh backend` 运行；生成的类型是否可用由 `scripts/remote-test.sh frontend` 的构建步骤把关。

### 替换规则

- 手写类型改成引用生成类型的别名，导出的名字保持不变，例如 `export type TreeImport = components['schemas']['TreeImportResponse']`。
- 逐个类型判断，分三类：
  - **可替换**：替换后 `tsc`、测试、lint 全过，且页面文件不需要改 → 替换。
  - **生成的更宽松**（如固定取值变成普通字符串）或**后端没有对应定义**（那约 50 个接口）→ 保留手写，列入汇报。
  - **两边确实不一致**（字段名不同、一边有一边没有、可空性不同且会影响页面）→ 不替换，保留手写，逐条列出交用户决定以哪边为准。
- 请求参数类型（`*Payload`、`*Request`）同样适用以上规则。

### 文档

`docs/DEVELOPMENT_GUIDE.md` 增加一小节：后端改了接口或数据模型后运行 `scripts/gen-api-types.sh`；新写前端类型时优先引用生成的类型。

无。线上页面和接口行为都不变；只是开发时多一个生成步骤，忘了做会让测试失败。
