# 待审核页候选词点选优化 — 设计文档

日期：2026-09-05
状态：已审核修订（v2，已采纳 Fable 评审意见）
影响范围：`review-intake` 待审核链路（后端提取 + 前端交互）
数据库迁移：无
接口变更：无（仅复用现有 `POST /keywords`）

## 一、问题与证据

### 现象

黑白名单待审核列表里，关键词捕获失败时，用户必须：悬停标题看完整路径 → 在浮层里选中文字 → 复制 → 粘贴进「确认关键词」输入框 → 点批准。五步操作，且在 Tooltip 浮层里选字体验极差。

### 根因

`app/services/classifier/keyword_extractor_service.py:146` 只对 `PurePosixPath(path).name`（文件名）做匹配，**从不查看上级目录名**；默认规则只有一条——找 `【】「」『』［］[]` 括号里的内容（调用方可传任意正则，但投递脚本不传，实际恒为默认值）。

用户素材大量来自 telegram 归档，人名写在父目录名里：

```
/…/telegram/163379-抖音 甜菜/163379 - video_2026-07-15_20-29-11 (2)_marked~1.mp4
/…/telegram/156930-秋秋/156930 - 回家地址 laopao.vip (11).mp4
/…/telegram/25478-#易直播_ #埃及凡 #是埃及凡呀 …/25481 - 5_6147779538538464336_(new)~1.mp4
```

这类路径结构上不可能被现有规则捕获。

### 生产数据佐证（2026-09-05 取自 organizer 库）

| 指标 | 数值 |
|---|---|
| 已批准待审项 | 272 条 |
| 其中当初「零候选」（纯手工确认） | 67 条（24.6%） |
| 批准词出现在完整路径中 | 271 / 272（99.6%） |
| 批准词出现在**文件名或直接父目录**中 | 270 / 272（99.3%） |
| 零候选那批里，答案在父目录名 | 43 / 67 |
| 零候选那批里，答案在文件名 | 23 / 67 |
| 零候选那批里，答案落在 `#hashtag` 内 | 6 / 67 |
| 零候选那批里，**只能靠自由文本切片拿到** | 61 / 67（91%） |

结论：答案几乎总在路径里，取材范围扩到「文件名 + 直接父目录」即覆盖 99.3%。不再向上追溯：只有 1 条答案在更上层，而更上层是 `/Volumes/docker1/SSD_cache/telegram` 这类固定仓库路径，切片全是噪声。

### 已排除的方案

初版曾提出「拿库里 1800 个已有关键词去路径里匹配，命中的当候选」。经数据验证后删除：已批准的 270 条里 257 条（95%）是当场新建的新词；抽样 60 条中路径命中库内**其它**已有词的仅 1 条（1.7%）。该来源作为可点选候选没有价值。库内比对能力保留，但**只用于给候选打状态标签**，不用于产生候选。

## 二、目标、非目标与已知取舍

### 目标

1. 捕获失败时，通过**点击候选标签 → 点批准**两次点击完成确认，全程无需复制粘贴。
2. 候选标签自带状态色，在列表上就能看出「这词库里已有」「点了会冲突」，而不是点批准后被接口报错拦下。

### 已知取舍（用户已知情并拍板）

**本次改动会增加屏幕上的内容片段，而不是减少。** 现状下零候选行的候选列是空的；改动后每行最多平铺 5 个片段，而露骨描述会被切进这些片段（如 `丝足控福利:丝袜足交,裸足交特写`）。

评审阶段提出过「只显示 hashtag/括号来源、自由文本折叠」的折中，被数据否决：67 条失败样本里只有 6 条答案在 hashtag 内，61 条（91%）必须靠自由文本切片才能拿到，折叠等于放弃收益。

也提供过「行内只放『选词』按钮、点开才显示」的方案（三次点击，屏幕默认零内容）。**用户明确选择平铺显示，接受露骨短词首次上屏。** 因此「× 一键加入忽略库」从可选功能升级为**必要功能**——它是这个取舍下唯一的收敛手段。

### 非目标（明确不做）

- 不做「自动填入最优候选 + 一键批准」。
- 不做批量批准。
- 不改 IINA 投递链路，`scripts/review_intake_shortcut.py` 与 lua 插件一行不动。
- 不做手动输入框的实时冲突提示。
- 不改动已批准/已忽略的历史记录。
- **不修 `suggest_similar` 的既有缺陷**（见 §3.5 已知问题），本次不承诺「相似词」能力。

## 三、候选词生成规则

新建纯函数模块 `app/services/review_intake_candidates.py`（与 `review_intake_service.py` 同级，遵循现有扁平模块风格）。

**旧函数 `extract_regex_keywords_from_path` 保留不动**，它另有两个调用方（`app/api/routes/extractor.py:223`、`:277`）和三个单测，不受本次改动影响。

### 3.1 取材范围

```
segments = [直接父目录名, 文件名（去扩展名）]
```

### 3.2 三条抽取规则

| 来源标记 | 规则 | 说明 |
|---|---|---|
| `hashtag` | `#([^\s#]+)`，捕获后 `strip("._- ")`（照抄现有 `_clean_keyword` 行为） | telegram 目录名里最干净的信号 |
| `bracket` | `[【「『［\[]([^】」』］\]]+)[】」』］\]]` | 沿用现有正则，取材范围扩大 |
| `segment` | 先剥流水号前缀 `^\d+\s*[-_.]?\s*`，挖掉已被 hashtag/bracket 命中的区间，再按 `[\s_,，:：\-/|~()（）\[\]【】]+` 切分 | 兜底，承担 91% 的命中 |

分隔符集合已按评审意见补入 `~ ( ) （ ）`——否则 `marked~1`、`(new)~1`、`(2)` 会作为整块进入下一步。

来源标记写入现有 `ReviewKeywordCandidate.source` 字段（原默认值 `manual_path_regex`，前端从未读取），**不新增字段**。

### 3.3 结构过滤（第一道闸）

**所有结构判断一律在 `normalize_keyword_text(x).casefold()` 之后进行**，这是评审指出的关键点：该函数会把 `_ - / ~ ( ) .` 等全部替换为空格（`registry_service.py:18-25`），因此 `marked~1` 实际变成 `marked 1`，若按原始文本做精确匹配，噪声表永远对不上。

命中任一条即丢弃：

- 归一化后长度 < 2 或 > 16（生产库黑白名单词长度：最短 2、中位数 5、九成 ≤ 10）
- 归一化后为纯数字或纯空白
- 归一化后按空格切分，**每一段都是纯数字**（覆盖 `2026 07 15`、`5 6147779538538464336`、`(2)`→`2`）
- 技术噪声表命中：归一化后的任一段落在固定集合内（常见扩展名、`marked`、`new`、`video`、`img`、`1080p`、`720p`、`4k` 等）。**这是技术噪声表，不是露骨词表**，内容稳定可硬编码
- 纯 ASCII 且归一化后长度 < 3

原设计中的日期正则 `\d{4}-\d{1,2}-\d{1,2}` 与 `\d{6,}` **已删除**：`-` 已是分隔符，日期在过滤前就被切成纯数字段，正则永远匹配不上；纯数字判定已完整覆盖。

### 3.4 忽略库过滤（第二道闸）

**一次性批量加载**：`list_entries(keyword_type="ignore", status="active", limit=5000)` 取出归一化文本集合（生产库现有 220 条），再对候选做集合判断。参照现有写法 `app/api/routes/extractor.py:29-34`，不逐候选查库。

命中者不进主列表，但保留在同一行的「更多」折叠里并标灰，允许用户反悔。

这是本设计压制露骨片段上屏的主力机制：不由开发者硬编码露骨词表，而是复用用户自己的忽略库，配合前端「×」按钮持续自净。

### 3.5 状态标注

对存活候选逐个调 `find_entry_by_keyword`：

| 条件 | `match_status` | 颜色 | 含义 |
|---|---|---|---|
| 命中且 `keyword_type == bucket` | `existing` | 绿 | 库里已有，这条八成不用再加 |
| 命中且 `keyword_type == 'ignore'` | `ignored` | 灰 | 已在忽略库 |
| 命中但类型既非 bucket 也非 ignore | `conflict` | 红 | 点批准会被接口拒绝（含 `tag`、`emby_*`，与 `approve` 的拒绝条件一致） |
| 未命中但 `suggest_similar` 有结果 | `similar` | 金 | 见下方已知问题 |
| 其余 | `new` | 蓝 | 新词，主要目标 |

**已知问题（本次不修）**：`suggest_similar`（`registry_service.py:494`）调用 `list_entries(status="active")` 时未传 `limit`，落到默认值 20，即只拿 20 条条目做相似度比对，库里其余 1780 条不参与。因此 `similar`（金色）在生产上基本不会触发。该缺陷是既有代码的问题，同时影响 `/keywords/similar-preview` 接口，属于共享服务改动，**不在本次范围内**，已单独向用户报告。本设计不依赖也不承诺该能力，行为维持现状。

**状态是投递时刻的快照**：`match_status` 在投递时算好并序列化进 `extracted_keywords_json`，读取时不重算。因此在 A 项批准了「甜菜」后，同一页 B 项上的「甜菜」仍显示为蓝色 `new`，直到该项被重新提取。这是现有行为，本次不改。

### 3.6 排序、去重与落库顺序

**去重**：同一归一化文本跨来源只保留排名最高的一条。

**候选组**（`new` / `similar` / 未被忽略库拦下的 `ignored`）排序键，依次比较，不做加权打分以保证可解释：

1. 来源优先级：`hashtag` > `bracket` > `segment`
2. 来自父目录的优先于来自文件名的（父目录命中 43 条 vs 文件名 23 条）
3. 归一化后长度落在 2–10 的优先
4. 其余按在路径中出现的先后顺序

**提示组**（`existing` / `conflict`）：不参与候选组排序，不占其名额，最多 3 个。

**落库顺序**：候选组（按上述排序）在前，提示组在后。这一点是必需的——`find_first_actionable_keyword`（`review_intake_service.py:334`）与前端 `defaultKeyword`（`ReviewIntakePage.tsx:61`）都取 JSON 里第一个可用词，若提示组在前会预填一个 `existing` 词。

**落库数量**：最多 12 条（候选组 ≤ 9 + 提示组 ≤ 3）。前端平铺前 5，其余进同行「更多」折叠。

**`examples` 字段置空**：现有实现给每个候选存 `examples=[raw_path]`（`keyword_extractor_service.py:161`），即把完整路径重复存 N 遍，这才是 JSON 体积的真正来源。新模块写入 `examples=[]`，历史数据不动。

### 3.7 预填策略（新增，评审指出的风险）

前端现有行为：`defaultKeyword` 会把第一个 `new/similar/existing` 候选自动填进「确认关键词」输入框（`ReviewIntakePage.tsx:61-66`、`104-114`）。零候选项目前填空。

新规则上线后，这些项会被自动预填排第一的切片——样例 1 会预填「抖音」而不是「甜菜」，用户不看直接点批准就会把噪声词写进白名单。

**决定**：只有 `source` 为 `hashtag` 或 `bracket` 的候选参与预填；`segment` 来源的**不预填**，输入框留空，靠用户点选。这与「用户自己确认」的核心诉求一致，也避免噪声词被误批准。

### 3.8 废弃的请求字段

`pattern` / `flags` / `group_index` / `limit` 四个字段存在于 `ReviewIntakeCreateRequest`、`ReviewIntakePathRequest`、`create_or_update`、`_extract_and_resolve_keywords`，现有测试也在传。

**决定**：字段全部保留以维持接口兼容（IINA 投递脚本不传，网页不传），但服务层不再使用 `pattern`/`flags`/`group_index`；`limit` 映射为落库候选上限（默认 12）。在 `docs/` 中标注三个正则相关字段已废弃。

## 四、页面交互

文件：`frontend/src/pages/ReviewIntakePage.tsx`

1. **候选标签可点击** —— 点一下把该词写进本行 `keywordDrafts`，再点批准。手动输入框保留不变。
2. **平铺前 5 + 「更多」折叠** —— 其余候选（含被忽略库拦下的灰标签）收在同一行的「更多」里，纯前端渲染，**不新增接口**。
3. **状态色 + 图例** —— 沿用现有 `MATCH_COLORS`；在待审面板标题栏加一行颜色图例。
4. **提示组置顶** —— 绿/红标签单独一行，前缀文案「库里已有」/「冲突」。
5. **候选标签带「×」** —— 仅在 `new` / `similar` 状态显示。`create_entry` 对已存在的归一化词直接返回现有条目且不改类型（`registry_service.py:141-147`），因此在 `existing`/`conflict` 上放 × 会静默无效。点击后经 Popconfirm 二次确认（误把人名加进忽略库后它将永不出现，很难察觉），再以 `keyword_type='ignore'` 写入关键词库。
6. **× 成功后前端本地移除** —— 因状态是投递时刻快照，重新拉列表不会让该标签变灰。× 成功后直接在本地把所有已加载行中同归一化文本的标签移除，这是最小改动。
7. **完整路径维持现状** —— 仍只在悬停 Tooltip 中出现，不常驻。

## 五、接口与数据兼容性

**接口变更：无。** 评审建议下砍掉了初版设计的两个新端点：

- ~~`GET /review-intake/items/{id}/segments`~~ —— 改为多存少量候选、前端「更多」折叠即可，不必为兜底场景引入第二条切片调用路径和一套过滤原因枚举。
- ~~`POST /review-intake/reextract`~~ —— 它的全部用途是给现存 12 条 pending 做一次性回填，之后新投递自然走新规则。一次性动作改为回归脚本的 `--apply-pending` 开关。

× 功能复用现有 `POST /keywords`（`keyword_type='ignore'`），前端在 `reviewIntake.ts` 加一个薄封装函数，不新建 api 模块。

**数据兼容**：无数据库迁移。`extracted_keywords_json` 是 Text 字段，`source` 是既有自由字符串字段，`parse_keyword_candidates` 用 `model_validate` 解析，历史数据可正常读取。已批准/已忽略记录不受影响。

## 六、验收标准

### 6.1 回归验证（主要成功标准）

新增脚本 `scripts/verify_review_intake_candidates.py`，用户可一键运行、输出为人话。

**只跑纯提取链路**：切片 → 结构过滤 → 忽略库过滤 → 排序。**不跑注册表状态标注**。

这是评审指出的数据泄漏必须规避的点：那 67 条的批准词正是因为批准动作已写进 `keyword_entries`，若跑完整管线，答案会被标成 `existing` 从而进入提示组、不进候选组前 5，按原口径会被系统性判为未命中；反过来把 `existing` 也算命中，又与真实场景（新人名不在库中）不符。

**两个指标，都要报**：

| 指标 | 样本 | 目标 |
|---|---|---|
| 零候选集命中率 | 67 条当初 `extracted_keywords_json='[]'` 的已批准记录 | **≥ 80%** |
| 旧命中集不退化率 | 205 条旧规则已产出候选的已批准记录 | **不低于旧规则**（接近 100%） |

第二个指标是评审补充的：新规则把 `hashtag` 排在 `bracket` 之前，父目录 hashtag 多的目录（telegram 频道名常带 4–6 个 `#`）可能把文件名括号里的正确答案挤出前 5。这批样本是当前用户体验的基线，退化比零候选没提升更糟。

**命中口径**：归一化后精确相等，答案出现在候选组前 5 内。另外报一个「候选组任意位置包含答案」的宽口径数字供参考。

**统计诚实性声明**：80% 是在同一批用来调规则的样本上测出的训练集成绩（第一节三条例子即来自这批），上线后以新投递的真实命中率为准。

**输出与隐私**：脚本默认只打印汇总数字，不打印任何路径与关键词明细；明细需显式加 `--show-details`。脚本为只读（除非显式加 `--apply-pending`），运行时连 `DATABASE_URL` 指向的库，文档注明应在服务器上或本地连生产只读运行。

### 6.2 单元测试

`tests/test_review_intake_candidates.py`，覆盖切片、结构过滤、去重、排序、落库顺序与数量上限、预填策略。

**测试夹具一律使用结构相同的脱敏假路径**，不得写入真实素材名、真实人名或露骨内容（遵循项目约定：真实业务数据不进测试夹具）。

### 6.3 上线后人工确认

生产页面对当前 12 条待审（含 3 条零候选）跑一次 `--apply-pending`，确认候选标签出现、可点选、状态色正确。

## 七、风险与回滚

| 风险 | 处置 |
|---|---|
| 露骨短词首次出现必定上屏 | 用户已知情并选择此方案；× 一键加忽略库 + 忽略库过滤形成收敛；上线前先跑回归脚本人工抽查前 5 |
| 新规则把旧的正确答案挤出前 5 | 验收指标 2 强制不退化 |
| 噪声词被自动预填后误批准 | §3.7：`segment` 来源不预填 |
| 候选状态过期（投递时刻快照） | 文档如实说明；× 后前端本地移除 |
| 误把人名加进忽略库 | Popconfirm 二次确认；可在关键词管理里改回 |

**回滚**：无迁移、无数据结构变更、无接口变更。`git revert` 对应 commit 后重新构建部署即可恢复。
